- **Feature 14 — no new date/timezone library.** The extraction LLM call is given "now" formatted in `profile.timezone` and returns naive local wall-clock ISO strings (no offset). `createEvent` sends those to Google alongside `timeZone: profile.timezone` in the request body — Google resolves the real UTC instant itself. - **Feature 14 — event times are stored in Mongo as their wall-clock numbers reinterpreted as UTC**, not real UTC instants (`parseLocalDateTime`/`toLocalDateTimeString` in `calendar-agent.ts` are an exact inverse pair for this). Lets `start`/`end` stay real `Date` values matching `EventDoc`'s existing schema and supports simple duration arithmetic (default 1-hour end) with zero timezone-math dependencies — the actual zone identity (`profile.timezone`) is only ever attached at the moment of calling Google, never baked into the stored value. Single-user app; if `profile.timezone` ever changed between propose and confirm the label would drift, an accepted low-probability risk.
- **Feature 14 — discard added, in scope by explicit developer decision** (build-plan.md itself only specified propose + confirm). Deletes the Mongo row outright rather than adding a third `status` value — nothing needs an audit trail of rejected proposals.
- **Feature 14 — `createEvent` throws on failure rather than degrading to an empty/fallback value**, a deliberate, documented divergence from `code-standards.md`'s general "services degrade gracefully" convention (`listUpcomingEvents` above it in the same file still degrades to `[]`). A write whose result flips a Mongo row to "confirmed" must not silently swallow failure — that would mark a proposal confirmed when nothing was created in Google. The throw is caught by `confirmProposedEvent`'s own try/catch.
